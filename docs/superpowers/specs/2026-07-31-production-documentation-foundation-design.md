# 生产级文档基础设施设计

**状态：** 已实施；生产流程采用与持续复审待维护者确认
**日期：** 2026-07-31  
**范围：** 本仓库的协作说明、设计记录、知识库和工程规范。

## 目标

建立一套版本受控、可审查、可执行的文档体系，使开发者和自动化代理能够在不依赖口头上下文的情况下安全地修改、部署和运行该数据平台。

该体系必须：

- 将长期约束、设计决策、运行知识和工程标准分开存放；
- 明确生产变更的测试、观察、审批与回滚门槛；
- 对 Kafka、Flink、Python collectors、Kubernetes 和状态服务的高风险变更提供可执行约束；
- 避免将未验证的运行状态或历史结论写成当前事实。

## 非目标

- 不替代现有 `README.md` 的项目概览。
- 不重写既有设计或实施计划。
- 不创建虚假的运行手册、SLO 数值、访问凭据或环境清单；此类内容必须由真实运行证据补全。
- 不清理、删除或提交当前工作区的既有未跟踪文件。

## 信息架构

```text
Instructions.md
design/
  README.md
wiki/
  README.md
docs/standards/
  README.md
  engineering.md
  data-contracts.md
  reliability-operations.md
  security.md
  testing-release.md
```

### `Instructions.md`

仓库级协作契约，面向开发者和自动化代理。它规定事实验证、架构边界、禁止项、变更前后门禁、文档更新责任和高风险基础设施操作的审批要求。它不记录易过期的部署状态。

### `design/`

存放面向未来变更的设计记录。`design/README.md` 定义文件命名、必需章节、决策状态和设计完成门槛。每项跨模块、数据契约、基础设施或可靠性变更都必须在实现前写入一份独立设计。

### `wiki/`

存放已验证、可复用的操作与领域知识。`wiki/README.md` 定义知识条目的来源、验证日期、所有者、复审周期和失效处理。运行手册、故障复盘、服务说明和术语表以后归入此处。

### `docs/standards/`

存放可执行的生产规范。`README.md` 给出优先级和例外流程；其余文档按专业领域限定编码、数据、可靠性、安全和发布行为。

## 核心规则

1. 事实、决策和计划必须分离：事实需附验证时间或证据；决策需说明替代方案与后果；计划不得描述为已完成。
2. 生产变更必须可回滚，并在变更前定义验证信号、失败条件和责任人。
3. Kafka topic、schema、消费者组、幂等键和外部副作用属于受控接口；任何变更都必须记录兼容性与迁移路径。
4. Secret 不得进入 Git、日志、错误信息、示例文件或设计文档；Kubernetes 配置必须通过受控 Secret 机制交付。
5. 所有服务必须具有可观测性、明确的失败行为和测试证据；无法验证的结论不得标记为完成。

## 验收标准

- 根目录存在 `Instructions.md`，并含范围、协作规则、架构边界、变更门禁和禁止项。
- `design/README.md` 和 `wiki/README.md` 可指导后续文档创建，且不伪造生产状态。
- `docs/standards/` 含索引及五份领域规范，覆盖工程、数据契约、可靠性/运行、安全、测试/发布。
- 所有 Markdown 链接为仓库内相对链接，标题层级一致，无 `TODO`、`TBD` 或未赋义的占位内容。
- 新增内容不修改业务代码、Kubernetes 清单或现有未跟踪文件。

## 风险与缓解

| 风险 | 缓解 |
| --- | --- |
| 规范与真实环境脱节 | 标记需要证据的内容；要求验证日期、来源和定期复审。 |
| 文档分散且难检索 | 以三个稳定入口分域，并在每个入口放置创建规则和导航。 |
| 规范变成不可执行的口号 | 每份规范使用明确的 MUST/MUST NOT、验收证据和例外审批要求。 |
| 现有脏工作区被污染 | 只添加目标文档；不格式化、删除、暂存或提交现有文件。 |

## 验证方式

实施后执行：

1. 检查所有新增文件存在且为 UTF-8 Markdown；
2. 运行 Markdown 链接与占位符扫描；
3. 审阅 Git diff，确认仅新增目标文档；
4. 由项目维护者确认规范适用于实际生产流程后，将状态改为“已采用”。
